STAGING DEPLOYMENT (Day 0 - Afternoon)
═══════════════════════════════════════════════════════════════════════════════

BACKEND DEPLOYMENT
──────────────────
□ Build Docker Image (if containerized)
  Command: docker build -f backend/Dockerfile -t appointment-service:staging .
  Verify: Image builds without errors
  
□ Push to Registry
  Command: docker push appointment-service:staging
  Verify: Image is accessible in registry

□ Deploy to Staging
  Option A - Kubernetes:
    Command: kubectl apply -f backend/k8s/appointment-service-staging.yaml
    Verify: Pod is running
    
  Option B - Direct Deploy:
    Command: dotnet publish -c Release -o ./publish
    Upload to: /app/services/appointment-service/
    Start Service: systemctl start appointment-service

□ Verify Backend Startup
  Check: Service logs for errors
  Endpoint Test: curl http://staging-api/api/v1/appointments/health
  Expected Response: {"status": "healthy"}

FRONTEND DEPLOYMENT
───────────────────
□ Build Angular Application
  Command: ng build --configuration staging
  Output: dist/appointment-ui/

□ Upload to CDN/Web Server
  Upload: dist/appointment-ui/* to staging web server
  Verify: Files uploaded successfully
  
□ Configure Staging API URL
  File: environment.staging.ts
  apiUrl: "https://staging-api.example.com/api/v1"
  
□ Verify Frontend Load
  Open: https://staging.example.com
  Expected: Angular app loads, no console errors
  Check: Network tab shows successful API calls

═══════════════════════════════════════════════════════════════════════════════
STAGING VALIDATION PERIOD (Day 1-2, 24+ Hours)
═══════════════════════════════════════════════════════════════════════════════

HOUR-BY-HOUR MONITORING
────────────────────────
Hour 1-2: Initial Stability
  □ Monitor application logs (no ERROR level logs)
  □ Check database performance (query times < 100ms)
  □ Verify no 500 errors in request logs
  □ Memory usage stable (no memory leaks)
  □ CPU usage baseline established

Hour 2-4: Load Testing
  □ Simulate 10 concurrent users scheduling appointments
    Tool: Apache JMeter or Postman
    Expected: All requests succeed, response time < 500ms
  
  □ Simulate 50 concurrent reads of appointment list
    Expected: All requests succeed, response time < 200ms
  
  □ Simulate appointment lifecycle: Schedule → Confirm → CheckIn → Complete
    Expected: All state transitions work correctly

Hour 4-8: Extended Testing
  □ Background reminder service test
    □ Create appointment scheduled for soon
    □ Verify reminder is scheduled
    □ Check reminder processing (logs)
    
  □ Error scenario testing
    □ Try invalid appointment IDs (should 404)
    □ Try confirming already confirmed appointment (should fail)
    □ Try cancelling completed appointment (should fail)
    □ Try scheduling in the past (should fail)
  
  □ Database backup verification
    □ Run backup procedure
    □ Verify backup integrity
    □ Test restore process
  
  □ Log aggregation
    □ Verify logs appear in centralized logging (if configured)
    □ Can search logs by request ID
    □ Error logs properly formatted

Hour 8-16: Soak Testing
  □ Continuous low-volume traffic (2 req/sec for 8 hours)
    Expected: No memory leaks, no performance degradation
    
  □ Monitor for any intermittent issues
  □ Verify database connections don't exhaust
  □ Check for connection pool issues

Hour 16-24: Final Validation
  □ Complete workflow test
    1. Schedule 5 appointments for different slots
    2. Confirm 3 of them
    3. Check-in to 2
    4. Complete 1
    5. Cancel 1 as PatientRequested
    Expected: All operations succeed, no errors
  
  □ Data consistency verification
    SELECT COUNT(*) FROM Appointments
    SELECT COUNT(*) FROM AppointmentReminders
    Verify counts match expectations
  
  □ Performance baseline established
    □ P50 latency: < 100ms
    □ P95 latency: < 300ms
    □ P99 latency: < 1000ms
    □ Error rate: < 0.1%
  
  □ Security scan
    □ No hardcoded credentials in logs
    □ No PII leaking in responses
    □ CORS headers correct
    □ Rate limiting working (try exceeding: 101 req/min should 429)
  
  □ Sign-off checklist
    □ QA Team: All tests passed
    □ DevOps: Deployment procedure verified
    □ Product: Feature works as specified
    □ Security: No vulnerabilities identified

PRODUCTION DEPLOYMENT PROCEDURE
────────────────────────────────
1. Create Database Snapshot (immutable backup)
   AWS/Azure: Create snapshot before migration
   Expected: Snapshot shows healthy database state

2. Apply Migrations to Production
   Command: dotnet ef database update --context AppointmentContext
   Expected: Migrations apply successfully
   Verify: New tables exist (Appointments, AppointmentReminders, etc.)

3. Deploy Backend to Production
   Kubernetes: kubectl apply -f backend/k8s/appointment-service-prod.yaml
   Direct: dotnet publish, upload, restart service
   Expected: Service starts, health check passes

4. Deploy Frontend to Production
   Upload: dist/appointment-ui/* to production CDN
   Invalidate cache if applicable
   Expected: Latest version served to users

5. Verify Production Endpoints
   GET /api/v1/appointments/health
   Expected: 200 OK

6. Run Sanity Tests on Production
   □ Schedule test appointment (then delete if possible, or keep for monitoring)
   □ Confirm test appointment
   □ Verify in database
   □ Clean up test data

═══════════════════════════════════════════════════════════════════════════════
ROLLBACK PROCEDURE (IF NEEDED)
═══════════════════════════════════════════════════════════════════════════════

DECISION TO ROLLBACK
────────────────────
Rollback immediately if ANY of these occur:
  ✗ Error rate > 5%
  ✗ Latency P95 > 2 seconds
  ✗ Database corruption detected
  ✗ Critical security vulnerability found
  ✗ Data loss occurring
  ✗ System unavailable for > 5 minutes

ROLLBACK STEPS
───────────────
1. Notify all stakeholders
   "Rolling back to previous version due to [reason]"
   
2. Stop current deployment
   Kubernetes: kubectl delete deployment appointment-service-prod
   Direct: systemctl stop appointment-service

3. Restore database from snapshot
   AWS/Azure: Restore database from pre-deployment snapshot
   Expected: Database returns to pre-deployment state
   
4. Deploy previous working version
   Kubernetes: kubectl apply -f backend/k8s/appointment-service-prod-v1.yaml
   Direct: Deploy previous published version
   
5. Verify health
   GET /api/v1/appointments/health
   Expected: 200 OK
   
6. Monitor for stabilization
   Wait 5 minutes, verify metrics return to normal
   
7. Post-mortem
   Once stable, investigate root cause
   Prepare fix for next deployment attempt

ESTIMATED ROLLBACK TIME: 5-10 minutes
