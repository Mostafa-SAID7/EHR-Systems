   Check: ReminderBackgroundService is running
   Method: Check if reminders processed in last 10 minutes

   Alert if: Service appears dead (no processing)

MONITORING METRICS & ALERTS
═══════════════════════════════════════════════════════════════════════════════

CRITICAL ALERTS (P1 - Immediate Action)
────────────────────────────────────────
Trigger Immediately if ANY of these occur:

1. Service Unavailable
   Condition: Health check fails for 2+ consecutive checks (1 minute)
   Action: Page on-call engineer immediately
   Response Time: 5 minutes

2. Error Rate Spike
   Condition: HTTP 5xx errors > 5% for 5 minutes
   Action: Investigate logs, consider rollback
   Threshold Alert: 100+ errors/minute

3. Database Down
   Condition: Database connection fails
   Action: Check DB status, restart if needed
   Recovery: Automatic failover (if configured)

4. Response Time Degradation
   Condition: P95 latency > 2 seconds for 5 minutes
   Action: Check database, review slow queries
   Acceptable P95: < 500ms

5. Memory Leak
   Condition: Memory usage increases > 90% of limit
   Action: Restart service gracefully
   Recovery: Automatic restart if configured

HIGH PRIORITY ALERTS (P2 - Investigate Today)
───────────────────────────────────────────────
1. Error Rate Increase
   Condition: HTTP 5xx errors > 1% (but < 5%)
   Action: Investigate root cause
   
2. Database Connection Pool Exhaustion
   Condition: Active connections > 80% of max
   Action: Check for query leaks, increase pool if needed
   
3. Disk Usage High
   Condition: Disk > 80%
   Action: Clean up logs, archive old data
   
4. Backup Failed
   Condition: Last backup > 24 hours old
   Action: Check backup job logs, retry backup

INFORMATIONAL ALERTS (P3 - Monitor Trend)
──────────────────────────────────────────
1. Gradually Increasing Latency
   Condition: P50 latency increases > 20% over 1 week
   Action: Plan performance optimization
   
2. Database Growth
   Condition: Database size increases > 10% per day
   Action: Monitor for unexpected growth
   
3. Warning Logs Increasing
   Condition: Warning count doubles in 1 day
   Action: Review warning source

RUNBOOK: Common Issues & Recovery
═══════════════════════════════════════════════════════════════════════════════

ISSUE: Service not responding (HTTP timeouts)
────────────────────────────────────────────
1. Check service status: systemctl status appointment-service
2. Check logs: tail -f /var/log/appointment-service/error.log
3. If crashed: systemctl restart appointment-service
4. Wait 30 seconds, verify health check passes
5. If still failing: Check database connectivity
6. If database is down: Follow database recovery procedure

ISSUE: High error rate (5xx errors)
───────────────────────────────────
1. Check recent logs for error patterns: grep ERROR /var/log/appointment-service/error.log
2. Check database: SELECT 1; (simple connectivity test)
3. Check database connections: SHOW PROCESSLIST;
4. If connection pool exhausted: Restart service
5. If database issues: Contact DBA

ISSUE: Slow response times (P95 > 1s)
──────────────────────────────────────
1. Check slow query log: SELECT * FROM slow_queries LIMIT 10
2. Check database indexes: Are appointment lookups indexed?
3. Restart database query cache: FLUSH QUERY CACHE;
4. If persists: Run ANALYZE TABLE on main tables
5. Last resort: Restart database service gracefully

ISSUE: Database connection failures
─────────────────────────────────────
1. Test connection: mysql -u user -p -h database-host
2. Check max connections: SHOW VARIABLES LIKE 'max_connections';
3. Check current connections: SHOW PROCESSLIST; | wc -l
4. If at max: Kill idle connections or restart service
5. Increase max_connections if consistently high
